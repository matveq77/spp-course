# Kanban Lite — курсовой проект «Современные платформы программирования»

Веб-приложение «канбан-доска» (облегчённый Trello) с командами, проектами, ролями,
**правами доступа, зашитыми в JWT**, и **обновлением в реальном времени без перезагрузки** (Server-Sent Events).

**Стек:** Python 3.11+ · FastAPI · SQLAlchemy 2 · SQLite (или PostgreSQL) · PyJWT · Vue 3 · SortableJS.
Фронтенд без сборки: Vue и SortableJS лежат в `static/vendor`, интернет не нужен.

## Запуск

```powershell
py -3 -m venv .venv                                   # обычный Python с python.org, не MSYS2
.venv\Scripts\python.exe -m pip install -r requirements.txt
.venv\Scripts\python.exe seed.py                       # демо-данные (пересоздаёт kanban.db)
.venv\Scripts\python.exe -m uvicorn app.main:app --reload --timeout-graceful-shutdown 2
```

> `--timeout-graceful-shutdown 2` обязателен с `--reload`: SSE-соединения не закрываются сами,
> и без этого флага uvicorn при перезагрузке бесконечно висит на «Waiting for connections to close».
> Браузеры после перезапуска переподключаются автоматически.

> Если `pip install` падает на сборке `pydantic-core` («Rust not found», «Unsupported platform»), значит,
> пакеты ставятся не в `.venv`, а в Python из MSYS2 (`C:\msys64\...`): под него нет готовых сборок.
> Вызывайте Python из `.venv` явно, как в командах выше.

Открыть http://localhost:8000. Документация API (Swagger): http://localhost:8000/docs

Тесты: `python -m pytest -q` (29 тестов: права, токены, 2FA, сессии, вложения, присутствие, спринты).

Существующую базу пересоздавать не нужно: при старте недостающие таблицы и колонки добавляются
автоматически (`app/db.py: migrate`).

**Демо realtime:** откройте `http://localhost:8000` под одним пользователем и
`http://127.0.0.1:8000` (другой origin → отдельный localStorage) под другим. Двигайте карточки, меняйте
роли — вторая вкладка обновится сама. Индикатор **Live** в шапке показывает активное SSE-соединение.

## Функциональность

- Регистрация/вход, access + refresh токены (refresh хранится в БД в виде хэша, ротируется при каждом обновлении).
- **Команды**: участники с ролями owner / admin / member, приглашение по логину, защита последнего владельца, выход из команды.
- **Проекты** внутри команд: ключ задач (`WEB-12`), видимость *team / private*, шаблоны досок (базовый, Scrum, пустой),
  явные роли manager / member / viewer, архивирование.
- **Доски** (несколько на проект), **колонки** с WIP-лимитами и флагом «Готово», перестановка drag-and-drop.
- **Карточки**: drag-and-drop между колонками, исполнители, метки, приоритет, срок (подсветка просрочки),
  оценка в story points, описание, чек-лист с прогрессом, комментарии с `@упоминаниями`, архив, история изменений.
- Фильтры на доске: поиск, метка, исполнитель, приоритет, «мои», «просроченные».
- **Realtime**: изменения доски, лента активности, уведомления, «кто сейчас смотрит доску» (presence), обновление прав.
- **Уведомления**: назначение на задачу, упоминание, комментарий к вашей задаче, завершение задачи, добавление в команду/проект.
- **Мои задачи** по всем проектам, **статистика** проекта (прогресс, приоритеты, нагрузка, активность за 14 дней).
- **Администрирование**: системные роли, блокировка пользователей (мгновенно отзывает доступ), онлайн-статистика.
- Страница **«JWT и права»** — показывает токен, его payload и права по проектам (удобно на защите).
- **Двухфакторная аутентификация (TOTP)**: QR-код для Google Authenticator / Яндекс Ключа, 10 одноразовых
  резервных кодов, вход в два шага, лимит попыток, сброс 2FA администратором.
- **Активные сессии**: браузер, ОС, IP, время входа и активности; завершение отдельной сессии или
  «выйти на всех других устройствах» / «выйти на всех устройствах» (доступ пропадает сразу). Смена пароля завершает остальные сессии.
- **Кто что делает в карточке**: аватары тех, кто открыл карточку (на доске и в самой карточке),
  индикатор «✏️ Иван редактирует описание» и проверка конфликта при одновременном сохранении описания.
- **Вложения**: файлы и картинки (drag-and-drop), превью и полноэкранный просмотр, лимит 10 МБ,
  скачивание только участникам проекта.
- **Спринты**: планирование из бэклога, старт с датой окончания (один активный спринт на проект),
  завершение с переносом незакрытых задач в новый / запланированный спринт или в бэклог,
  **burndown-диаграмма** (story points или количество задач), итоги завершённых спринтов,
  фильтр «спринт» и бейдж спринта на доске.
- **Настройки интерфейса**: светлая/тёмная тема, цвет акцента, компактные карточки, звук и тосты уведомлений.

## Модель прав (RBAC в JWT)

Роли трёх уровней раскрываются в конкретные права (`app/permissions.py`):

| Уровень | Роль | Права |
|---|---|---|
| Система | admin | `sys:admin` — доступ ко всему |
| Команда | owner | `team:read, team:update, team:delete, team:members, project:create` |
| | admin | то же без `team:delete` |
| | member | `team:read` |
| Проект | manager | `project:read/update/delete/members, board:manage, label:manage, card:create/update/move/delete/assign, comment:create/moderate` |
| | member | `project:read, card:create/update/move/assign, comment:create` |
| | viewer | `project:read, comment:create` |

Итоговая роль в проекте = максимум из: явной роли в проекте; `manager`, если пользователь owner/admin команды;
`viewer`, если он участник команды, а проект с видимостью *team*.

Payload access-токена:

```json
{
  "sub": "3", "usr": "ivan", "name": "Иван Петров", "pv": 4, "type": "access", "exp": 1767000000,
  "role": "user", "sys": [],
  "teams":    { "1": { "role": "member", "perms": ["team:read"] } },
  "projects": { "1": { "role": "member", "perms": ["project:read", "card:create", "card:move", "..."] } }
}
```

Проверка на сервере — **без запросов к таблицам ролей**, только по токену:

```python
@router.post("/cards/{card_id}/move")
def move_card(card_id: int, body: CardMove, me: Principal = Depends(get_principal), ...):
    me.require_project(project.id, P.CARD_MOVE)   # 403, если в JWT нет права
```

Клиент тоже читает права из токена и прячет недоступные кнопки (`can('card:create', projectId)`).

### Проблема устаревших прав и её решение

Права в JWT «замораживаются» на момент выдачи. Решение:

1. Access-токен живёт 15 минут, клиент заранее молча обновляет его по refresh-токену.
2. У пользователя есть счётчик `perm_version` (claim `pv`). При любом изменении прав (добавили в команду,
   сменили роль, удалили проект, заблокировали) счётчик растёт. Сервер держит версии в in-memory кэше и
   отклоняет токены со старым `pv` ответом `401 token_outdated` — то есть отзыв мгновенный.
3. Одновременно по SSE пользователю уходит событие `auth.refresh` — клиент перевыпускает токен,
   переподключает поток событий и перерисовывает интерфейс с новыми правами. Перезагружать страницу не нужно.

## Двухфакторная аутентификация

TOTP по RFC 6238 реализован на стандартной библиотеке (`app/totp.py`, есть тест на эталонный вектор из RFC).

1. `POST /api/me/2fa/setup` — сервер генерирует секрет, отдаёт `otpauth://` URI и QR-код (SVG).
2. `POST /api/me/2fa/enable {code}` — 2FA включается только после первого верного кода;
   в ответе 10 резервных кодов (в БД хранятся только их SHA-256 хэши, показываются один раз).
3. Вход: `POST /api/auth/login` при включённой 2FA возвращает не токены, а `challenge_token`
   (JWT с `type: "2fa"`, живёт 5 минут, им нельзя обращаться к API). Затем
   `POST /api/auth/login/2fa {challenge_token, code}` → токены.
4. Защита: не более 5 попыток на один challenge, код из уже использованного 30-секундного окна
   повторно не принимается, резервный код одноразовый.

## Сессии

Сессия = цепочка refresh-токенов одного входа: при ротации `session_id` сохраняется, в access-токене
он лежит в claim `sid` (так сервер понимает, какая сессия «текущая»). Завершение сессии отзывает её
refresh-токен и увеличивает `perm_version` пользователя: все его access-токены тут же перестают
приниматься. Текущая вкладка незаметно получает новый токен, остальные устройства выходят на экран входа.

## Спринты и burndown

- Задача попадает в спринт полем `cards.sprint_id`; менеджер создаёт, запускает и завершает спринты
  (`board:manage`), участник планирует задачи (`card:update`).
- Остаток работы = сумма story points (или число) задач спринта, которые не лежат в колонке «Готово».
- Снимок остатка за текущий день (`sprint_days`) обновляется автоматически: SQLAlchemy-хук `after_flush`
  замечает изменения карточек и колонок, а `before_commit` пересчитывает снимок активного спринта проекта.
  Фоновых задач не нужно: если в какой-то день ничего не менялось, график берёт значение предыдущего дня.
- На графике три линии: фактический остаток, идеальная линия (от объёма на старте до нуля к дате окончания)
  и объём спринта (видно, когда задачи добавляли или убирали в середине спринта).
- При завершении фиксируются итоги (выполнено задач и SP, сколько перенесено), а история burndown сохраняется.

## Присутствие и вложения

- Клиент сообщает `POST /api/presence {board_id, card_id, editing, seq}`, сервер хранит это у SSE-соединения
  и рассылает событие `presence` всем на доске. `seq` защищает от гонок: запоздавший запрос не
  перетирает более свежее состояние. При закрытии вкладки соединение рвётся и присутствие исчезает само.
- Перед сохранением описания клиент сверяет текущую версию на сервере с той, что была при начале
  правки. Если её успели изменить, пользователь видит чужую версию и решает: перезаписать или объединить.
- Файлы лежат в `uploads/` под случайными именами, метаданные в таблице `attachments`. Картинка
  определяется по сигнатуре файла, а не по расширению (SVG картинкой не считается: в нём могут быть
  скрипты). Не-картинки отдаются как `application/octet-stream` + `attachment`, с `nosniff` и `no-store`.
  При удалении карточки, доски, проекта или команды файлы стираются с диска после успешного commit.

## Realtime (Server-Sent Events)

`GET /api/events?token=<JWT>` — долгоживущий HTTP-ответ `text/event-stream`. Выбран SSE, а не WebSocket:
обновления идут только от сервера к клиенту, а изменения клиент и так отправляет обычным REST.
SSE работает поверх обычного HTTP, браузер сам переподключается при обрыве.

- `app/events.py` — брокер: у каждого соединения своя `asyncio.Queue`; событие адресуется проекту, команде или
  конкретным пользователям и фильтруется по правам из токена, с которым открыто соединение.
- События ставятся в очередь внутри транзакции и публикуются **только после успешного commit**
  (`services.queue_event` + SQLAlchemy `after_commit`), поэтому клиенты не увидят откатившиеся изменения.
- Типы событий: `board.changed`, `activity`, `notification`, `presence`, `project.*`, `team.*`, `auth.refresh`.
- Keep-alive каждые 15 с, чтобы прокси не рвали соединение.

## Структура

```
app/
  main.py          приложение FastAPI, статика
  config.py        настройки (DATABASE_URL, JWT_SECRET, TTL)
  db.py            подключение к БД
  models.py        ORM-модели (User, Team, Project, Board, Column, Card, Label, Comment, ...)
  permissions.py   роли → права, сборка claims для JWT
  security.py      хэширование паролей, выпуск/проверка JWT, refresh-токены, perm_version
  deps.py          Principal — пользователь из токена, require_project/require_team
  events.py        брокер SSE-событий и presence
  services.py      журнал активности, уведомления, события после commit
  schemas.py       Pydantic-схемы входных данных
  serializers.py   ORM → JSON
  totp.py          TOTP (RFC 6238), QR-код, резервные коды
  sprints.py       расчёт остатка спринта, снимки и ряды burndown
  twofactor.py     проверка второго фактора
  routers/         auth, account (2FA, сессии), users (профиль, уведомления, админка), teams,
                   projects, boards, sprints, attachments, realtime
static/            SPA на Vue 3 (js/app.js, views.js, board.js, api.js, store.js, ui.js)
tests/             pytest: права в JWT, отзыв токенов, роли, WIP-лимиты, уведомления, подделка токена
seed.py            демо-данные
```

## Переменные окружения

| Переменная | По умолчанию | |
|---|---|---|
| `DATABASE_URL` | `sqlite:///kanban.db` | например `postgresql+psycopg://user:pass@localhost/kanban` (нужен `pip install psycopg[binary]`) |
| `JWT_SECRET` | dev-значение | **обязательно поменять** в продакшене |
| `ACCESS_TOKEN_TTL_MIN` | 15 | время жизни access-токена |
| `REFRESH_TOKEN_TTL_DAYS` | 14 | время жизни refresh-токена |
| `UPLOAD_DIR` | `uploads/` | куда сохранять вложения |
| `MAX_UPLOAD_MB` | 10 | максимальный размер файла |

Ограничение: брокер событий и кэш `perm_version` живут в памяти процесса, поэтому запускать нужно один
воркер uvicorn. Для горизонтального масштабирования брокер заменяется на Redis Pub/Sub.
